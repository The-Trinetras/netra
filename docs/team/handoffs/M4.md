## 2. Defects found and fixed in the earlier commits

Reviewing `e30ca7a`/`a2ddeef` rather than only the new work:

1. **Retransmission reported a false failure.** `propose_event` clears the
   pending question via `mark_answered`, so a retransmitted turn found
   nothing pending and returned `failed` — for a turn that had actually
   succeeded. Fixed by deriving the replay lookup from the same
   `auth.request_id` the attempt id comes from: `find_committed_attempt`
   is now checked **first** in `_run_evaluate_answer` (before any model
   call) and again inside `propose_event` itself, so the authoritative
   layer is idempotent rather than trusting the caller.
2. **The runtime instruction was never loaded.** `TutorServices.instruction`
   defaulted to `""` and nothing read `prompts/tutor.md`, so production
   would have run the Tutor with no grounding, privacy or format rules at
   all. Fixed with `load_tutor_instruction()` as the field default, pinned
   by `test_services_load_the_instruction_by_default_into_the_prompt`.
3. **Rubric feedback cited no evidence.** The rubric path resolved
   evidence to ground its feedback but dropped the ids from the result
   (fixed during the previous pass; test added).
4. **`AssessmentHistoryRepository.get` had no "absent" outcome.** It
   returned `AssessmentAttempt`, leaving "unknown id" undefined. Now
   `Optional[...]`, with absent (None) and unauthorized (raise) kept
   distinct — the replay lookup depends on that difference.

Reviewed and confirmed correct, no change needed:
- The Tutor reaches persistence only through `LearningService.propose_event`
  with `state.auth`; it never touches a repository directly.
- A result carrying `attempt_id` is already committed. **M1 integration
  rule: do not re-propose an event that has an `attempt_id`.** If it were
  re-proposed, `propose_event` replays (same turn) or raises
  `QuestionNotPendingError` (new turn) — it cannot double-commit.
- `_parse_verdict` is structural only; its docstring now says explicitly
  that a successful parse establishes nothing about whether the grade or
  feedback is supported by the source.
- Nothing records generated or sent text as heard: the only committed
  record is an answered attempt, and `concept_exposed` is proposed on the
  wire but never committed.

## 3. Decision packets — PROPOSED, not approved

A model checkpoint does not grant cross-owner or human approval.

### D2 — Optional-check evidence grounding (owners: M3 + M4)

`quiz/validator.py::validate_draft_is_grounded` stays `NotImplementedError`.

- **Recommended:** require each `QuestionDraft` to carry the
  `evidence_id`s it was generated from, and approve only if every claim
  span in prompt and answer key is entailed by the text of those
  authorized evidence items, checked by a bounded non-agent entailment
  step whose failures are recorded, not retried.
- **Alternatives:** (a) Tutor self-check — cheapest, but the component
  being checked does the checking; (b) human-reviewed question bank —
  strongest, but no authoring pipeline exists and it blocks generated
  questions entirely.
- **Failure behaviour:** fail closed. No persist, no delivery, no attempt.
- **Affected files:** `quiz/validator.py`, `quiz/models.py`
  (`QuestionDraft`/`ApprovedQuestion` gain `evidence_refs`),
  `tutor/agent.py::_run_check_understanding`.
- **Acceptance cases:** question supported by evidence → approved;
  answer key contradicting evidence → refused; question about material
  absent from evidence → refused; evidence unresolved → refused;
  refusal delivers and persists nothing.
- **Test seam already in place:** `TutorServices.grounding_validator`
  defaults to the production fail-closed validator. Tests inject an
  approving stand-in to exercise delivery downstream. **That seam is not
  grounding and must not be reported as grounding integration.**

### D3 — Factual history (owners: M4 record shape, M2 persistence, M1 wire, M5 presentation)

`AssessmentAttempt` requires `question_id`/`question_version`/`answer`/
`outcome`, so it can represent only a graded answer. `concept_exposed`,
`hint_used` and delivered activity have nowhere to go, which is why
`propose_event` raises `UnrepresentableLearningEventError` for them.

**Minimum records proposed** — a new append-only table beside, not
replacing, `assessment_attempts`:

```
LearningActivityEvent
  event_id      UUID      deterministic from (request_id, lesson_id, kind, ordinal)
  account_id    UUID      authorization scope; never model-supplied
  session_id    UUID
  lesson_id     UUID
  concept_id    str|None
  kind          enum      explanation_generated | assistance_given
                          | student_reasoning_recorded | feedback_generated
  evidence_ids  str[]
  text          str       the delivered or stated content, verbatim
  attempt_id    UUID|None links assistance/feedback to its attempt
  occurred_at   datetime
```

Properties, each tied to an authority:
- `kind` says **generated**, never "delivered"/"heard": sent, played and
  acknowledged stay distinct, and only M1/M5's playback-ack path may
  record what was actually heard.
- **No** status/mastery field and **no** "Studied — understanding not
  tested" enum value — that phrase is wording M5 renders from the absence
  of attempts, not a stored value.
- Append-only, deterministic `event_id`, so at-least-once delivery and
  turn retries collapse — same rule as `attempt_id`.
- `review_requested` is not carried forward; it stays a legacy value.

**ASR/correction provenance — what actually needs to cross the wire.**
Most provenance is service-side and must *not* be added to the handoff:
`transcript_status` is already pinned to `final` by the protocol, and the
Session/speech service holds the ASR record. The Tutor needs exactly one
thing it cannot derive: whether the utterance it is grading **replaced an
earlier transcript for the same pending question**, because that changes
whether a differing answer is a correction or a second attempt. Minimum
wire change, M1 to review:

```
CoordinatorToTutorHandoff.utterance_provenance = {
  "supersedes_prior_utterance": bool
} | null
```

The original transcript text itself stays service-side and is joined to
the attempt by the Learning service when it commits, populating the
existing `AnswerSubmission.original_transcript`/`corrected_text` fields —
which the Tutor currently cannot populate honestly and therefore leaves
unset.

- **Affected files:** `assessment/models.py`, a new M2 migration +
  repository, `shared/contracts/agent/v1/coordinator_to_tutor.schema.json`
  and `coordinator/handoff.py` (the one optional field), M5 presentation.
- **Compatibility:** additive and optional; a `null`/absent
  `utterance_provenance` behaves exactly as today. The new table does not
  alter `assessment_attempts`.
- **Tests:** activity recorded without an answer; assistance linked to
  its attempt; replayed turn creates one event; correction recorded
  without a second attempt; no label field anywhere in the record.

### D4 — Neo4j projection (owners: M2 boundary, M4 representation)

Two independent blockers, both still open.

1. **Removed-scope conflict.** The only projection edge, `MasteryEdge`,
   requires a `LearningStatus`, so projecting it means running
   `derive_status_from_history` — i.e. completing the automatic mastery
   labelling current scope removed. **Proposed instead:** a factual
   `AttemptedEdge {account_id, concept_id, attempt_id, outcome,
   hints_used, occurred_at}` carrying the recorded outcome of a specific
   attempt, never an aggregate judgment about the student. `MasteryEdge`
   and its Cypher stay in place untouched as legacy.
2. **Worker authorization boundary.** `ProjectAssessmentAttemptJob.handle`
   receives only `account_id`/`attempt_id` and no `AuthContext`, while
   every learning repository requires one, and no worker-scoped auth
   concept exists. **Proposed:** do not invent a privileged `AuthContext`.
   Have `propose_event` write the outbox row inside the same transaction
   as the attempt, with the payload carrying everything the projection
   needs (`account_id`, `concept_id`, `attempt_id`, `outcome`,
   `hints_used`, `occurred_at`), so the worker projects from the event
   and never re-reads account-scoped state. This requires an
   outbox-writing port callable from `netra_api` — **M2's call**, since
   today `OutboxRepository` lives in `netra_worker.runtime` and an
   `netra_api` → `netra_worker` import would be a new cross-package
   dependency.
- **Affected files:** `learning/graph/neo4j.py`, `graph/projection.py`,
  `worker/jobs/learning_projection/neo4j.py`, `assessment/service.py`,
  plus M2's outbox port and migration.
- **Tests (need a designated test database, see §4):** attempt + outbox
  committed atomically; projection replay is idempotent; an older event
  cannot overwrite newer projected state; projection failure leaves the
  attempt committed.

## 5. Integration instructions

**M1 (Coordinator/session):**
- Call `run_turn(state, services)`; build state with `build_turn_state`,
  passing the *originating* `TurnBudget` instance (a fresh one is
  rejected).
- A `ProposedLearningEvent` with `attempt_id` set is **already committed** —
  report it, do not re-propose it.
- `status == "awaiting_student_answer"` ends the turn; the Tutor never
  polls. Restore `pending_question_id` verbatim on reconnect.
- Send `continue_lesson` **with** `pending_question` to request a hint;
  `check_understanding` only once the student has agreed to a check.
- `hint_used` proposals mean the Session service should increment
  `PendingQuestionRef.hints_used`; the Tutor cannot write it.
- Review the one proposed optional handoff field in D3.

**M2 (data/worker):** the D4 outbox boundary and the D3 table/migration
are yours; `find_committed_attempt` needs `AssessmentHistoryRepository.get`
to return `None` for an unknown id and raise for another account's.

**M3 (evidence):** D2 grounding is a joint decision. `EvidenceRef.
source_version_id` is a free-form string in `agent/v1` while
`Evidence.source_version_id` is a `UUID` — the Tutor cannot cross-check
the declared version and relies entirely on the resolver.

**M5 (client):** public segment kinds now in use are `explanation`,
`hint`, `question`, `correction`. "Studied — understanding not tested" is
wording you render from the absence of attempts, never a value we send.

## Blocking gates

1. **D2** evidence grounding (M3+M4) — blocks production question delivery.
2. **D3** factual-history record + the one optional handoff field
   (M4/M2/M1/M5) — blocks durable activity, reasoning, feedback and
   assistance records, and the evidence check at commit.
3. **D4** outbox/worker boundary + factual projection shape (M2+M4) —
   blocks Neo4j projection and atomic attempt/outbox commit.
4. **Environment:** a CPython 3.13.15 interpreter, and a designated test
   database, before persistence/atomicity claims can be made at all.
