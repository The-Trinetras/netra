## What was implemented and why it needed no cross-owner review

### 1. `LearningService.propose_event` (assessment/service.py)

Previously validated shape/ownership then raised `NotImplementedError`
unconditionally. Now:

- Only commits `event_type == "answer_evaluated"`. `AssessmentAttempt`
  requires `question_id`/`question_version`/`answer`/`outcome` as
  non-optional fields — it has no representation for `concept_exposed`,
  `hint_used`, or `review_requested` (those describe activity with no
  question/answer at all). Forcing them into an answer-shaped row would
  fabricate a question that was never asked, which CLAUDE.md forbids
  ("never fabricate ... a successful extraction result" / "fail closed").
  These now raise `UnrepresentableLearningEventError`, replacing the
  blanket `NotImplementedError`. **This is the concrete evidence for the
  factual-history schema gap the M4 prompt's item 4 asks about — see
  "Owner decisions needed" below.**
- For `answer_evaluated`: resolves the target question via the existing
  `PendingQuestionRepository.get_pending`; rejects if it is not pending
  (`QuestionNotPendingError` — covers both "never asked"/"not yours" and
  "already answered", satisfying the "finality" check learning.md
  requires) or at a different version (`QuestionVersionMismatchError`).
  On success it builds an `AssessmentAttempt`, calls
  `AssessmentHistoryRepository.append`, then
  `PendingQuestionRepository.mark_answered`.
- Replay safety: `attempt_id` is derived deterministically via
  `uuid5(namespace, f"{auth.request_id}:{question_id}:{question_version}")`.
  `AuthContext.request_id` is already the stable per-turn identifier
  message-flow.md documents ("request_id is minted once per logical user
  action ... reused verbatim if that same action must be retransmitted"),
  supplied by the application layer, never the model. A retried
  `turn.submit` therefore reproduces the same `attempt_id`, which is what
  makes `AssessmentHistoryRepository.append`'s documented "idempotent by
  attempt_id" behaviour actually reachable for a duplicate submission.
  This needed no new wire field and no `LearningEventProposal` field for
  an operation ID — it reuses data already flowing through the existing
  signature.
- Added `evaluated_by: Optional[EvaluatedBy]` to `LearningEventProposal`
  (internal model, not a wire contract) because `AssessmentAttempt.
  evaluated_by` is required and nothing populated it before.

Evidence/rubric grounding is explicitly **not** checked here:
`ApprovedQuestion` carries no `evidence_refs` field today, and
`netra_api.learning.quiz.validator.validate_draft_is_grounded` is
deliberately `NotImplementedError` pending the same evidence-grounding
product decision (see that module's docstring — it says guessing the
definition of "supported by evidence" would make policy by default).
`propose_event` cannot enforce a check against data the model does not
carry; documented as a gap, not silently skipped.

Why this needed no Opus/cross-owner review: no shared/contracts change,
no migration, no new persistent schema, no worker-runtime wiring. It
implements logic against already-defined Protocols
(`AssessmentHistoryRepository`, `PendingQuestionRepository`), exactly
the "implement against the Protocol, not the driver" pattern already
established by `netra_api.coordinator.router.route_turn`. The one design
choice made — deriving `attempt_id` from `auth.request_id` — is
reversible, contained entirely inside `learning/assessment/service.py`,
and does not touch any field another owner's code reads.

### 2. `DeterministicTutorEvaluator` (evaluation/scripts/)

Structurally implements `evaluation.scripts.interfaces.
TutorBehaviorEvaluator`. Five deterministic, structural checks against
an already-produced `TutorToCoordinatorResult` and its originating
`CoordinatorToTutorHandoff`:

- `cites-evidence` — `evidence_ids` is non-empty.
- `evidence-ids-authorized` — every cited id is one the handoff actually
  supplied (catches an uncited-but-authorized gap, not semantic support —
  message-flow.md: "A valid citation alone does not prove semantic
  support").
- `responded` — a non-`failed` result delivers at least one public
  segment (waived when `status == "failed"`).
- `pending-question-consistency` — `status == "awaiting_student_answer"`
  iff `pending_question_id` is set.
- `learning-events-target-handoff-concepts` — every proposed learning
  event's `concept_id` is one of the handoff's `target_concept_ids`
  (agent-boundaries.md: "Tutor cannot ... invent concepts").

An unregistered `criterion_id` or unregistered `rubric_id` raises
(`UnknownCriterionError` / `UnknownRubricError`) rather than silently
skipping — fail-closed, matching CLAUDE.md. Ragas/Prometheus-2
integration is explicitly out of scope and not touched (no network call,
no model download, no provider SDK anywhere in this module).

No `evaluation/rubrics/` or `evaluation/cases/` data files were added —
this session only implemented and tested the evaluator itself; populating
real rubrics/cases is a product-content decision, not mechanical.

## Not implemented — genuinely blocked, not silently skipped

Per the M4 prompt's "IMPLEMENT IN ORDER" list:

1. **Tutor turn loop** (`api/src/netra_api/learning/tutor/agent.py:
   run_turn`) — still raises `NotImplementedError`. This is the core
   cross-agent-interface deliverable (dispatches on the shared
   `agent/v1` handoff's `mode`, decides when to call `GroqTutorProvider`,
   `EvidenceResolver`, `QuizGenerator`, and how the result maps onto
   `TutorToCoordinatorResult`) and touches replay/budget semantics
   directly. Blocked on the Opus checkpoint below.
2. **Optional checks** (`check_understanding` mode / quiz generation
   path) — additionally and specifically blocked on
   `validate_draft_is_grounded`'s evidence-grounding decision, which
   message-flow.md lists as "Pending decision" and the source module's
   own docstring says guessing it "would make it policy by default."
   Not attempted.
3. Learning proposal validation/commits — **done** for `answer_evaluated`
   (see above); `concept_exposed`/`hint_used`/`review_requested` remain
   blocked on the factual-history schema (item 4).
4. **Factual-history schema/handoff proposal** — not drafted this
   session; see "Owner decisions needed."
5. **Relevant-history selection / bounded lesson context** — not
   started; depends on (1) and (4).
6. **Neo4j projection wiring** (`worker/src/netra_worker/jobs/
   learning_projection/neo4j.py`) — not implemented. Every worker job in
   this repository (ingestion, multimedia, search_projection,
   review_scheduler, learning_projection) is left in the identical
   documented-stub shape pending a worker-side provider/service-wiring
   decision that ownership.md assigns to M2 ("M2 coordinated migrations/
   worker runtime"). Implementing this job alone, differently from every
   sibling job, would diverge from that established repo-wide pattern
   without the M2 review the ownership table requires. Additionally,
   `ProjectAssessmentAttemptJob.handle` only receives `account_id`/
   `attempt_id` (no `AuthContext`), and every learning repository method
   requires one — there is no "system"/worker-scoped `AuthContext`
   concept anywhere in the codebase. A promising resolution (have
   `LearningService.propose_event` compute what the projection needs and
   put it directly in the outbox payload at commit time, since it already
   holds a valid `auth`) was identified but not implemented, because it
   would add a new API→worker (`netra_api` → `netra_worker.runtime.
   outbox`) dependency, which agent-boundaries.md's ownership table
   marks as needing the same cross-owner (M2) review as the worker-side
   wiring it would replace.
7. **Evaluation** — deterministic evaluator done (see above);
   Ragas/Prometheus-2 integration correctly not attempted (explicitly
   deferred, needs authorization this task does not grant).

## Owner decisions needed (Opus checkpoint packet)

1. **Tutor turn loop design** — `run_turn`'s mode-dispatch, its provider/
   service dependency-injection signature (it currently takes only
   `TutorTurnState`; real dispatch needs `GroqTutorProvider`,
   `EvidenceResolver`, `QuizGenerator`, `ObjectiveGrader` at minimum),
   and how `TutorToCoordinatorResult.decision_summary`/
   `proposed_learning_events` get populated per mode. This is the
   central `agent/v1` cross-workstream interface deliverable of this
   prompt; a wrong shape here reaches M1 (Coordinator caller) and M5
   (public output) immediately.
2. **Optional-check evidence-grounding criterion** — what "the question
   and its answer key are supported by the selected evidence" means
   operationally (entailment check against evidence text? Tutor
   self-check? human-reviewed bank?). Explicitly flagged pending in
   message-flow.md and quiz/validator.py; each option implies a
   different pipeline and cost. M3/M4 per current-scope.md's evidence
   rules.
3. **Factual-history schema/handoff proposal** (M1/M2/M5 per the M4
   prompt) — concrete shape for representing `concept_exposed`/
   `hint_used`/delivered-activity/stated-reasoning/feedback/assistance
   as committable records, since `AssessmentAttempt` cannot today. This
   also determines whether `shared/contracts/agent/v1/*.schema.json`'s
   `assessment_summaries`/`review_requested` fields need a coordinated
   migration (agent-boundaries.md already flags this as open).
4. **Worker-side service/auth wiring for learning_projection** (M2) —
   either a worker-scoped `AuthContext` concept, or the outbox-payload
   approach sketched above (API-side service computes and embeds what
   the projection needs at commit time), or something else M2 prefers.
   Affects every worker job identically, not just M4's.

No code/configuration change in this session assumes an answer to any
of the above; each blocked area was left exactly as found (an existing,
documented stub) rather than guessed.
