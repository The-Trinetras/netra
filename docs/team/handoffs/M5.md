## Starting point (read before reviewing the diff)

The scaffold already implemented, correctly, before this pass:
- `Protocol/` typed envelopes/DTOs/enums matching `shared/contracts/protocol/v1/*`.
- `Networking/ConnectionManager` — stable `request_id` retransmission for
  `turn.submit`/`navigation.command` (decision F, 2026-09-12), fresh
  `message_id`/`sequence` per frame.
- `Audio/InterruptionController`, `Audio/BinaryAudioFrameProcessor`,
  `Audio/BinaryAudioFrame` — local-first STOP, generation fencing, disconnect
  fencing, strict header parsing/sequence admission.
- `Audio/PlaybackController`, `Audio/PlaybackAcknowledger` — pause vs. stop
  semantics, `started`/`progress`/`completed` ack classification.
- `State/ClientSessionState` — session version, applied-request dedup.
- A single `MainWindow` with a transcript list, input box and four buttons
  (Send/Stop/Previous/Repeat/Next); this was a control shell, not the
  Library/Study/Conversation/Preferences journey the AgentSpec/M5 guide call for.

## What this pass implemented

1. **Four accessible views** (`Views/LibraryView`, `StudyView`,
   `ConversationView`, `PreferencesView`) hosted in `MainWindow` as a
   `TabControl` (native UI-Automation `TabItem`/`SelectionItem` support, so
   NVDA announces tab name/position without any custom Automation Peer).
   Each view is a plain `UserControl` bound to its own view model
   (`ShellViewModel` composes `LibraryViewModel`, `StudyViewModel`,
   `ConversationViewModel`, `PreferencesViewModel`). Tab order and
   `AutomationProperties.Name` are set on every interactive control.
2. **Library view / accessible selection**: `Microsoft.Win32.OpenFileDialog`
   (the standard accessible Windows file picker) restricted to `.pdf` and a
   short list of lecture container extensions. A cancelled dialog
   (`ShowDialog() != true`) adds nothing to the library and sends nothing —
   verified by `LibraryViewModelTests`. A selected file becomes a
   `LibraryEntry` with an explicit `LibrarySourceStatus` (`Selected` →
   `Processing` → `Ready`/`Failed`); status transitions are announced through
   the shared live region, and the current implementation drives them from a
   local `IFixtureSourcePreparationService` **explicitly labelled as a
   fixture** (see Gap 1) rather than a real ingestion call, so it never
   claims a server-side mutation succeeded.
3. **Video discovery (YouTube) scaffold**: `Library/IVideoDiscoveryService`
   + a fixture implementation return numbered results for a typed query;
   the view retains the exact selected result (`SelectedVideoResult`) the
   way `client.md` requires ("present numbered results and retain the exact
   selected result"). No network call, no player, no web-view — see Gap 2.
4. **Study view / passage-object exploration**: `Study/DetectedObject` +
   `StudyViewModel` render a fixture-labelled outline (headings, one figure,
   one table, one equation) with deterministic "explore" / "back to reading"
   commands that restore the exact prior focused item — no LLM call, no
   regenerated labels, matching `client.md`'s "never regenerate authoritative
   figure labels" and "exact return to reading". Backed by
   `StudyViewModelTests` (`ExploreObject_ThenReturn_RestoresExactPriorFocus`).
   Real content is blocked on Gap 3.
5. **Conversation view**: carries over the existing transcript/turn-submit/
   navigation-command behaviour from the old `MainViewModel`
   (`ConversationViewModel` now), unchanged in its protocol behaviour, plus
   two real fixes:
   - **UI-thread marshaling** (`Threading/IUiDispatcher` +
     `WpfUiDispatcher`): `ConnectionManager.MessageReceived` and
     `ISpeechInputService.TranscriptReceived` fire from the WebSocket
     receive loop / a future recognition-provider thread, not the UI
     thread. The old code mutated `ObservableCollection<TranscriptLine>`
     directly from those handlers, which is a genuine bug (WPF collection
     views are not thread-safe off the UI thread; this can throw or corrupt
     the bound `ListBox`, silently under a debugger and audibly to NVDA
     under load). Every UI mutation from a non-UI-thread event now goes
     through `IUiDispatcher.Invoke`. A `SynchronousUiDispatcher` test double
     makes this deterministic in tests.
   - **Generation admission wiring**: `response.segment` receipt now calls
     `BinaryAudioFrameProcessor.AdmitGeneration(segment.GenerationId)`
     exactly once per new generation id, before appending the transcript
     line — closing the gap the old scaffold left open (frames could never
     be admitted because nothing ever called `AdmitGeneration`). See Gap 4
     for what remains unwired (turning admitted bytes into speaker output).
   - **`session.snapshot`/`quiz.question`/`error` handling**: these were
     `// TODO` no-ops. They now reconcile `ClientSessionState`
     (`TryAdvanceSessionVersion`, interaction mode, pending-question/result-set
     references) and surface `error.message` through the shared status live
     region instead of silently dropping the frame. Never expose
     `error.code`/`retryable` as spoken text beyond the safe `message` field,
     per the error schema's own "safe/accessible text only" constraint.
6. **Activation hotkey + push-to-talk + press-to-interrupt**
   (`Accessibility/GlobalHotKeyService`, `Accessibility/PushToTalkController`):
   - Activation hotkey (`Ctrl+Alt+N`, chosen only as a placeholder — see Gap 5)
     registered via `RegisterHotKey`/`UnregisterHotKey` (user32, P/Invoke —
     no new NuGet dependency) so it works even when Netra is not the
     foreground window. Its handler only restores/focuses the main window
     (`Activate()` + `FocusService.MoveFocusToFirstFocusable`); it never
     touches `ISpeechInputService`, matching "Activation focuses Netra
     without opening the microphone."
   - Push-to-talk is a local (in-window) key-down/key-up pair, not a global
     hotkey: `client.md` requires push-to-talk to capture only while held,
     and a global low-level keyboard hook capable of reliable key-up
     detection needs a native hook (`SetWindowsHookEx`) with materially
     larger scope/risk than `RegisterHotKey`. Scoping it to the window
     keeps today's change to a plain WPF `PreviewKeyDown`/`PreviewKeyUp`
     pair. Key-down: if local playback is active, call
     `InterruptionController.StopAsync(CancelReason.UserStop)` first
     (press-to-interrupt), then `ISpeechInputService.StartListeningAsync`.
     Key-up: `StopListening()`. No VAD, no hands-free capture, no audio
     retained outside the held window.
   - `CancelReason` has no dedicated "interrupted by push-to-talk" value
     (only `user_stop`/`new_turn`/`navigation`/`client_shutdown` are
     approved on the wire); press-to-interrupt reuses `user_stop` rather
     than inventing a fifth enum member. Flagged for M1 review — see Gap 6.
   - Immediate STOP (`Escape`, existing) is unchanged: still fully local
     before any network call.
7. **Preferences/status view**: shows connection state
   (`Connected`/`Reconnecting`/`Disconnected`, client-local only, never a
   wire field per `data-ownership.md`), current interaction mode, and an
   explicit **"Fixture data — not a live server response"** indicator that
   is on whenever Library/Study content is fixture-sourced (always, today).
   This is the "expose real progress, failure and reduced modes without
   misleading reassurance" requirement made visible rather than asserted.
8. **Tests added**: `LibraryViewModelTests`, `StudyViewModelTests`,
   `ConversationViewModelDispatchTests` (UI-thread marshaling + generation
   admission), `SessionSnapshotHandlingTests`. Existing 7 test files
   untouched except where `MainViewModel` renamed to `ConversationViewModel`
   forced a reference update (`MessageFactoryTests` etc. did not reference it
   and are untouched).

## Explicit gaps — decisions this pass could not make

1. **Source preparation is a fixture.** No ingestion/upload HTTP contract is
   defined for the client to call (`docs/team/ownership.md`: "Concrete
   ingestion/retrieval/persistence still needed" under M2). `Library/IFixtureSourcePreparationService`
   is a test-only double; a real implementation needs M2's upload endpoint
   shape (multipart? presigned S3 URL? job-id polling?) before this can stop
   being a fixture. Flag: **M2, M1** (HTTP surface + job-status contract,
   `shared/contracts/jobs/v1/job.schema.json` is currently empty).
2. **YouTube embedded player and search are both unimplemented by design.**
   `client.md`/`current-scope.md` require M3/M5 review of the desktop
   web-view dependency before installation; this pass proposes concrete
   requirements rather than installing anything:
   - A WPF-hostable web view (`Microsoft.Web.WebView2` is the only
     realistic candidate on `net10.0-windows`; no other option avoids a
     second UI framework) to host the official YouTube iframe API.
   - A player-control payload: at minimum `seek(seconds)`, `pause()`,
     `play()`, `getCurrentTime()`, and a "player ready"/"video unavailable"
     signal — none of which exist in `shared/contracts/` today.
   - A discovery payload: `docs/architecture/message-flow.md` does not
     define a wire shape for search results; `IVideoDiscoveryService`'s
     fixture return type is this pass's proposal, not a contract.
   Flag: **M3, M5, M1** (dependency approval + payload definition).
3. **No client-visible evidence/multimedia contract exists yet.**
   `docs/team/ownership.md` lists reading-block/evidence models as
   server-internal (`api/src/netra_api/content/...`,
   `api/src/netra_api/multimedia/...|`), not wire types. `Study/DetectedObject`
   is therefore fixture data (Ohm's-law fixture: `fig02`, `tbl01`, `eq01`,
   matching the AgentSpec §4 walkthrough) so the exploration *interaction*
   (list → select → announce → return) can be built and tested now, but no
   real figure/table/equation can render until M2/M3 define and expose that
   payload. Flag: **M2, M3, M5**.
4. **Admitted audio bytes still never reach a speaker.**
   `BinaryAudioFrameProcessor.AudioBytesAdmitted` now actually fires (Gap
   closed: generation admission is wired), but `WPF.MediaPlayer` (used by
   `PlaybackController`) plays from a `Uri`/stream, not incremental byte
   chunks pushed frame-by-frame. Turning admitted PCM/opus chunks into
   audible output needs either (a) a duplex bridge (write chunks to a
   growing temp file / named pipe and open that as the player's source) or
   (b) a lower-level playback API (`NAudio`, `System.Windows.Media.MediaPlayer`
   cannot do streaming append). Adding a library here needs the same
   approval `client.md` requires for any audio library. Flag: **M1, M5**
   (this is exactly the "coordinate the missing total frame-size limit with
   M1 rather than inventing it" item, plus a playback-library decision).
5. **Hotkey choices are placeholders, not reviewed shortcuts.**
   `Ctrl+Alt+N` (activation) risks colliding with other running
   applications' global hotkeys (`RegisterHotKey` fails silently-by-design
   into a logged, non-fatal no-op if already claimed — see
   `GlobalHotKeyService.TryRegister`). AgentSpec §8 requires "exact
   shortcuts must pass conflict tests," which needs a real Windows session
   to run. Flag: **M5** (needs a live Windows conflict-test pass before
   these are final).
6. **`CancelReason` has no press-to-interrupt value.** Reusing `user_stop`
   is a semantic approximation, not a contract change. Flag: **M1** (only
   M1 can add a wire enum member, and only with a version review).
7. **No real ASR/TTS provider is wired.** `MicrophoneCapture`/
   `ScreenReaderService` are unchanged scaffolds; `PushToTalkController`
   drives the same interface, so a provider becomes usable by implementing
   `ISpeechInputService` without touching hotkey/view code. Provider choice
   (Deepgram/ElevenLabs per `runtime-baseline.md`) and credential handling
   are explicitly M1-owned ("Backend speech/session interfaces require M1
   review"). Flag: **M1**.
8. **Total binary-frame size limit remains undefined** (unchanged from
   before this pass — `message-flow.md`'s "Unresolved decisions retained"
   table). `BinaryAudioFrame.MaxHeaderBytes` (16 KiB) is unchanged; no total
   frame cap was invented. Flag: **M1** (transport-hardening decision).

## Acceptance evidence

Environment note: `dotnet --list-sdks` on this machine reports `10.0.103`
only; `client/global.json` pins `10.0.401` with `rollForward: disable`. This
is a pre-existing environment gap, not something this pass changed.
`dotnet build`/`dotnet test` were run twice:

1. **As pinned** (`global.json` present, unmodified): `dotnet build
   Netra.sln` fails immediately with `NETSDK1141`-style "Requested SDK
   version: 10.0.401 ... A compatible .NET SDK was not found," before any
   compilation is attempted. This is the accurate, honest result against
   the approved runtime baseline and is unchanged by this pass.
2. **Diagnostic-only compile/test check**: `client/global.json` was
   temporarily renamed (not edited — the exact same bytes), a build/test
   pass was run against the only installed SDK (`10.0.103`), and the file
   was renamed back immediately afterward. `git diff -- client/global.json`
   after restoring shows no difference — this was a read-only diagnostic
   detour, not a baseline change, and is reported as such rather than as
   the approved runtime's result:
   - `dotnet build Netra.sln`: one real compile error surfaced and was
     fixed (`PreferencesViewModel.cs` was missing `using
     Netra.Desktop.Protocol.Dto;` for `SessionInteractionMode`). Second
     build: **succeeded**, 0 errors, 29 warnings — all pre-existing-pattern
     `CS0067` ("event is never used") on hand-rolled test doubles'
     unused `Disconnected`/`ConnectionFaulted`/`BinaryMessageReceived`/
     `SnapshotChanged`/`PlaybackCompleted` events, the same pattern already
     present in the untouched pre-existing test files (e.g.
     `InterruptionControllerTests.FakeWebSocketClient`).
   - `dotnet test Netra.sln`: **Passed! Failed: 0, Passed: 53, Skipped: 0,
     Total: 53.** This includes all 7 pre-existing test files (unchanged,
     confirming no regression) plus the 5 new files this pass added
     (`LibraryViewModelTests`, `StudyViewModelTests`,
     `ConversationViewModelDispatchTests`, `SessionSnapshotHandlingTests`,
     `PushToTalkControllerTests`).
   - Build/test artifacts (`bin/`, `obj/`) were deleted afterward; both are
     already covered by the repository `.gitignore`.

No NuGet restore was invoked implicitly beyond what `dotnet build` itself
performs; the project has zero external package references in
`Netra.Desktop.csproj` (the test project's three `PackageReference`s were
already present and unchanged), so this is not a dependency-resolution
concern.

**What this evidence does and does not establish**: it verifies the C#
compiles and every automated unit-test assertion in this pass holds against
the *installed* SDK. It does **not** verify against the *approved* SDK
(10.0.401 is not installed here), and it says nothing about WPF rendering,
UI Automation tree shape, NVDA announcement text, or any live-Windows
interaction — see the gates section below for those.

## Windows/NVDA/hardware gates — status

Not run: this session has no attached Windows-with-NVDA target, no
microphone, no speaker output and no YouTube API access. Per the M5 prompt's
ACCEPTANCE section ("If Windows/NVDA/player access is absent, mark those

  table/graph exploration, lecture-question, STOP and exact-return tasks.

  checked programmatically, but "does NVDA/another app still get the
  gesture" needs a live session).

(dedup, fencing, dispatcher marshaling, session-snapshot reconciliation,
fixture cancellation-uploads-nothing) is covered by the xUnit tests listed
above and is real, not simulated, verification of that logic.
