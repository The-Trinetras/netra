## Pass 1 — Learning proposal validation and commit

`LearningService.propose_event` previously validated shape/ownership then
raised `NotImplementedError`. It now:

- Commits only `event_type == "answer_evaluated"`. `AssessmentAttempt`
  requires `question_id`/`question_version`/`answer`/`outcome` as
  non-optional fields and has no representation for `concept_exposed`,
  `hint_used` or `review_requested`. Forcing those into an answer-shaped
  row would fabricate a question that was never asked. They now raise
  `UnrepresentableLearningEventError` — this is the concrete evidence
  behind the D3 proposal below.
- Runs ownership → shape → representability → question identity +
  finality → version → replay, in that order, mirroring learning.md's
  required validation list.
- Derives `attempt_id` deterministically as
  `uuid5(ns, f"{auth.request_id}:{question_id}:{question_version}")`.
  `AuthContext.request_id` is already the stable per-turn identifier
  message-flow.md documents ("minted once per logical user action ...
  reused verbatim if that same action must be retransmitted"), supplied
  by the application layer and never by a model. A retried `turn.submit`
  therefore reproduces the same `attempt_id`, which is what makes
  `AssessmentHistoryRepository.append`'s documented "idempotent by
  attempt_id" behaviour reachable for a real duplicate submission. No new
  wire field and no proposal-level operation id was needed.

Evidence/rubric grounding is deliberately **not** checked here:
`ApprovedQuestion` carries no `evidence_refs`, so there is no data to
check against. Recorded as a gap, not silently skipped.

## Pass 2 — decisions taken, and their limits

### D1 — Tutor turn loop: RESOLVED and implemented

`api/src/netra_api/learning/tutor/` is M4-owned, the prompt orders this
item first, and implementing it required no `shared/contracts/` change —
so this was M4's call to make, not a cross-owner one. `run_turn` is now
`async` and takes a `TutorServices` bundle of the already-existing
Protocols (provider, evidence resolver, pending-question repository,
learning service, optional quiz generator). No new boundary was invented.

Decisions inside it, with rationale:

1. **The Tutor calls `LearningService.propose_event` as a bounded tool,
   rather than returning rich proposals over the wire.**
   `TutorToCoordinatorResult.proposed_learning_events` carries only
   `{event_type, concept_id, attempt_id}` — no answer, no outcome — so
   the Coordinator structurally *cannot* reconstruct a
   `LearningEventProposal` from the wire result. The contract's existing
   `attempt_id` field only makes sense if the commit happens Tutor-side
   and the resulting id is reported back. `assessment/service.py`'s own
   docstring already said this ("the Tutor calls propose_event as a
   bounded tool call"). Agent/service separation is preserved because
   `LearningService` performs every authorization and validation check
   and the Tutor cannot bypass it.
2. **A choice-kind answer that matches no option is not graded.**
   `grade_objective_answer` documents "unmatched is INCORRECT", which is
   correct *as a grading function*. But whether to grade at all is a
   separate, upstream decision. The Tutor uses the existing
   `resolve_submitted_option` to ask "is this a recognisable attempt?",
   and only calls the grader once an option matched. An unmatched
   utterance — a decline, an aside, a misheard unit, a correction —
   returns a clarification with the pending question unchanged and
   records nothing. This is what satisfies "correction is not
   automatically failure" and "a declined check must not create a grade"
   without changing `grader.py` and without inventing a phrase table for
   "skip"/"consent" (the trap `session/commands.py` explicitly warns
   against).
3. **Rubric grading uses a strict verdict format; anything else fails
   closed.** `TutorModelDecision` is free text, so the instruction
   requires a first line of exactly `CORRECT`/`PARTIAL`/`INCORRECT`/
   `NOT_AN_ANSWER`. Unparseable output, or a verdict with no feedback,
   records nothing and re-asks. A grade inferred from prose would write a
   wrong fact into append-only history.
4. **`concept_exposed` is proposed on the wire but never committed.**
   Committing it would hit `UnrepresentableLearningEventError`. Emitting
   it keeps the delivered-activity record visible as the gap it is,
   rather than dropping it silently, and costs no budget.
5. **Budget exhaustion returns `status="failed"`, but the grounding gap
   raises.** coordinator.md requires a "bounded failure response" on
   exhaustion. The grounding `NotImplementedError` is deliberately left
   to propagate: the result contract has no way to say "blocked on an
   unmade product decision", and collapsing it into `failed` would make a
   known architectural gap indistinguishable from a provider outage.

### D3 — Factual-history schema: PROPOSAL ONLY (needs M1/M2/M5)

Not implemented. A proposal is not a contract approval.

**Why a change is needed.** Current scope requires recording delivered
study activity, each answer, student-stated reasoning, feedback and
assistance *separately*. `AssessmentAttempt` can express exactly one of
those (a graded answer). Three of the four `LearningEventType` values
have nowhere to go.

**Proposed shape** — a new append-only record alongside, not replacing,
`assessment_attempts`:

```
LearningActivityEvent
  event_id        UUID      replay-safe, derived from (request_id, lesson_id, kind, ordinal)
  account_id      UUID      authorization scope; never model-supplied
  session_id      UUID
  lesson_id       UUID
  concept_id      str|None  None where the activity is not concept-scoped
  kind            enum      explanation_generated | assistance_given
                            | student_reasoning_recorded | feedback_generated
  evidence_ids    str[]     what grounded it
  text            str       the actual delivered or stated content
  attempt_id      UUID|None links assistance/feedback to the attempt it belongs to
  occurred_at     datetime
```

Deliberate properties, each tied to an authority:

- **`kind` says "generated", not "delivered" or "heard".** Delivered,
  played and acknowledged remain distinct (current-scope.md), and the
  Tutor only ever knows that it produced text. Playback acknowledgement
  is M1/M5's path and must not be inferred here.
- **No status/mastery/label field, and no
  "Studied — understanding not tested" enum value.** That phrase is
  activity wording rendered by M5 from the *absence* of attempts, not a
  stored value. Automatic labels are a removed requirement.
- **Append-only, with a deterministic `event_id`** so at-least-once
  delivery and turn retries collapse instead of duplicating, matching the
  `attempt_id` derivation already shipped in pass 1.
- **`review_requested` is not carried forward.** It stays a legacy
  compatibility value in the v1 schema; nothing new should emit it.

**Also needed, and a separate M1 decision:** the handoff carries only
`original_utterance: str`, with no ASR/correction provenance. So
`AnswerSubmission.original_transcript`/`corrected_text` can never be
populated — the Tutor cannot honestly claim an answer was transcribed or
corrected. Recording transcript correction as factual history requires an
optional provenance object on `CoordinatorToTutorHandoff`, which is a
`shared/contracts/agent/` change and therefore M1's call with M4.

**Affected consumers:** M2 (table + migration + repository), M1 (handoff
field, if provenance is adopted), M5 (public presentation of activity
history), M4 (emit + relevant-history selection, item 5, which is blocked
on this).

**Validation/replay semantics:** written in the same transaction as the
mutation it describes; idempotent on `event_id`; a projection failure
never reverses it.

### D4 — Worker projection wiring: NOT RESOLVED

Two independent blockers, either of which is disqualifying on its own:

1. **Ownership.** Every worker job in the repo (ingestion, multimedia,
   search_projection, review_scheduler, learning_projection) is the same
   documented stub pending a worker-side service-wiring decision that
   ownership.md assigns to M2. `ProjectAssessmentAttemptJob.handle`
   receives only `account_id`/`attempt_id` and no `AuthContext`, while
   every learning repository method requires one; there is no
   system/worker-scoped auth concept anywhere in the codebase. A
   promising fix — have `propose_event` put what the projection needs
   into the outbox payload at commit time, since it already holds a valid
   `auth` — would introduce a new `netra_api` → `netra_worker` dependency,
   which needs the same M2 review.
2. **A removed-scope conflict that M4 should flag rather than resolve
   alone.** The only projection edge that exists, `MasteryEdge`, requires
   a `LearningStatus`, and producing one means running
   `derive_status_from_history` — i.e. completing exactly the automatic
   mastery labelling that current-scope.md removed. Item 6 says to
   "isolate removed status/review behaviour from new current-scope
   execution". So a current-scope projection needs a *factual activity*
   edge rather than a mastery edge, whose shape depends on D3. Building
   the projection now would either resurrect removed scope or invent a
   graph shape ahead of the record shape it derives from.

## Findings for other owners

1. **Type inconsistency across the evidence boundary (M1/M2/M4).**
   `EvidenceRef.source_version_id` is a free-form `string` in
   `shared/contracts/agent/v1/` (the committed example uses
   `"src-ver-104"`), while `Evidence.source_version_id` is a `UUID` in
   `content/retrieval/evidence.py`. The Tutor therefore cannot
   cross-check that resolved evidence came from the version the handoff
   declared — it relies entirely on the resolver's own check. Worth
   reconciling before that redundant check is expected to work.
2. **Residual leak risk on rubric grading (M4/evaluation).** The rubric
   and reference answer are sent to the model because rubric grading is
   the Tutor's job. Nothing in code can stop a model from echoing them
   back inside its feedback; the runtime instruction forbids it, and the
   structural code path never copies them into a public segment. This
   needs an evaluation criterion, not a code fix.
3. **Both runtime prompt files were empty and nothing loads them.**
   `prompts/tutor.md` is now written, and `TutorServices.instruction`
   takes its text so prompt assembly stays pure. `coordinator/prompts/
   coordinator.md` is still empty — M1's call.
