## F6 / M3-MATHML-1: fidelity decision request (for Arshad) — Arun, 20 September 2026

Branch `arun/F6-mathml-decision`, stacked on P3. `render_mathml` still raises;
it is implemented only after Arshad agrees the fidelity below (or amends it).
The rest of F6 (real figure, table and equation exploration) waits for
Ashlin's C6 evidence payload.

**Why it is not on the critical path for NVDA users.** WPF cannot render
MathML. What a screen-reader user hears is the navigable `EquationTree`
(`spoken_form` per node), which exists already. MathML only matters if the
client later shows equations in WebView2, where NVDA with MathCAT reads
MathML; that is a later client choice.

**Proposed fidelity** (the M3 handoff's mapping, made exact):

1. Presentation MathML only: one `<math xmlns="http://www.w3.org/1998/Math/MathML">`
   element. No Content MathML, no `semantics`/`annotation`.
2. From `EquationNode.kind` and the literal `symbol` (XML-escaped; `spoken_form`
   never goes into MathML): OPERAND → `mn` when the symbol is a number, otherwise
   `mi`; OPERATOR → `mo`; FUNCTION → `mrow` of `mi` (name), `mo`
   U+2061 (function application) and the argument; FRACTION → `mfrac`;
   GROUP → `mrow`, with `mo` fences only when the source shows them (a symbol
   of `(`…`)` on the group); SUPERSCRIPT → `msup`; SUBSCRIPT → `msub`.
3. A unit on an operand follows it as `mo` U+2062 (invisible times) and
   `mi mathvariant="normal"`, so `2 A` stays two tokens and the unit survives.
4. Structure is checked, never repaired: FRACTION, SUPERSCRIPT and SUBSCRIPT
   need exactly two children, OPERAND and OPERATOR need a symbol and no
   children. Otherwise a typed error, and no partial MathML.
5. **Only verified trees are rendered.** A tree whose `extraction_source` is
   still GENERATED gets no MathML (`mathml` stays null), because multimedia.md
   forbids presenting an unverified extraction as authoritative.
6. Tests: V = I × R and a fraction/superscript case, exact expected strings;
   escaping of `<`, `&`; each structural refusal; the GENERATED refusal.

Decision needed from Arshad: accept 1–6, or name the changes. Recorded in
integration status "Decisions needed" as M3-MATHML-1.

## F8 / M5-VIDEO lecture player — Arun, 20 September 2026

Branch `arun/F8-lecture-player`, stacked on F2 (merge F1, F3, C8, F2 first).

**What works on the client.** A new **Lecture** tab plays a YouTube lecture
chosen with **Play this lecture** on a library result, or pasted as a YouTube
link. WebView2 (pinned in F1) hosts Netra's own bundled page
(`Video/Player/player.html`, served as `https://netra-player.example/` from the
app folder), which drives YouTube's IFrame API (`pauseVideo`, `seekTo`,
`getCurrentTime`) in privacy-enhanced mode (`youtube-nocookie.com`). The web
view is locked down: only that page at the top level, only YouTube `/embed/`
frames, no new windows, downloads, devtools, context menus, browser shortcuts,
script dialogs or permissions (the page can never get the microphone), and
messages are accepted only from the page. Everything is operated from WPF with
named buttons and letter keys: **K** play or pause, **J**/**L** back or forward
10 seconds, **T** where am I, **C** continue, **D** describe. The web view is
out of the Tab order, so focus and NVDA stay on Netra's controls. Times are
spoken in words ("3 minutes 5 seconds"), not "3:05".

**Pause first, exact resume.** Push-to-talk, a typed question or **D** pause a
playing lecture before anything else, so the microphone never records the
lecture and Netra never speaks over it. The time kept is the one the player
reports once paused; if it does not answer, no time is kept (never a guess).
The lecture stays paused while Netra answers; only **C** (or **K**) resumes, by
seeking to exactly the kept position. Moving back or forward while paused
replaces the kept position. Push-to-talk opens the microphone without waiting
for the time report, so no first words are lost.

**Readiness, two lines.** "Playback: …" comes from the player itself (ready,
or not available with the reason: owner disallows embedding, removed or
private, not a valid video, no WebView2 Runtime, YouTube unreachable).
"Analysis: …" says honestly that this server does not report lecture analysis
yet. Neither is ever merged into one "ready".

**Not yet (needs the server).** The kept time is not sent with the question,
and **D** cannot produce a description: both need C8 (`turn.submit.video_context`,
the readiness route) and, for search results, C7 plus a server-side
`VideoAsset`. Library search results are still fixture data with fake ids, so
**Play this lecture** says so; a pasted YouTube link plays for real.

## F2 / D-CRED sign-in screen — Arun, 20 September 2026

Branch `arun/F2-sign-in`, stacked on C8 (merge F1, F3, C8 first).

**What works on the client.** In live mode, a computer with no stored
credential opens the **Sign in to Netra** dialog once the main window is up:
NVDA hears the title and the instruction and lands in the "Access code" box;
Enter signs in, Escape cancels. The code box is a plain text box on purpose,
so a screen-reader user can read back a one-time code to find a typing
mistake (a password box reads only "star"). The code is exchanged once over
HTTPS for a device credential, which is written to Windows Credential Manager
(`CredWriteW`, generic credential `Netra:api`, this user on this computer, not
roaming; the same UTF-16 form `cmdkey` writes). Every outcome is one spoken
sentence: accepted, not accepted (mistyped, used or expired), server not ready
for access codes, no connection, timed out, or saved for this run only when
Windows refuses to store it (a consumed one-time code must not be wasted). A
refusal keeps the code in the box, selected, for correction. Neither the code
nor the credential appears in a status, a log or a URL.

When the server no longer accepts the stored credential at start-up, the
dialog opens once with the reason; it never loops. Preferences and status now
has **Sign in with an access code…** and **Sign out of Netra on this
computer…** (confirmed in a standard message box, No by default). Signing in
or out clears the conversation and source list, closes the connection on
purpose (no reconnect attempts), and starts a new session for whoever signs in
next, so one student's session never reaches the next student's.

Also fixed here: **D-open-1**. `NetraWebSocketClient.CloseAsync` now sends a
real close handshake and reports one disconnect; it used to abort the socket.
Sign-in failures anywhere (library, reconnect) now say where to sign in.

### C2 review from the client side (for Arshad, before C2 merges)

The client is built to this proposal, isolated in `HttpAccessCodeExchange`
(one class to change if C2 differs):

1. `POST /v1/access-codes/exchange`, no Authorization header, body
   `{request_id: uuid, access_code: string}`; the code never in a URL.
2. `200 {device_credential: string, expires_at: date-time | null}`.
3. **Retry-safe:** the same `request_id` and code within a short window returns
   the same credential. The client retries once under the same request id when
   the response was lost; without this, a dropped response burns the code.
4. Refusals use the existing `{error: {code, message, retryable}}` body: a
   wrong, used or expired code is `AUTHORIZATION_DENIED` (one wording for all
   three, so codes cannot be probed); rate limits are retryable. A missing route
   (404/405) is told as "this server does not accept access codes yet".
5. No device name or machine identifier is sent (privacy). If revocation needs
   a label, it can be a later, student-chosen one.
6. An expired or revoked credential keeps producing 401/403 at the WebSocket
   upgrade and on HTTP; the client asks for a new code and replaces the stored
   credential only after a successful exchange.

## F3 / D-MIC voice capture (client side) — Arun, 20 September 2026

Branch `arun/F3-voice-capture`, stacked on `arun/F1-nuget-lock` (merge F1
first). Builds on Codex's uncommitted WinMM layer from the same item.

**What works on the client.** Holding F9 opens the microphone through WinMM
`waveIn` (P/Invoke, no NuGet; 8 × 20 ms native buffers on a dedicated thread)
and sends `asr.start`. Audio is held locally (bounded at 6 s) until the server
answers `asr.ready`, then streams as 100 ms binary frames; releasing F9 sends
the last frame with `end_of_utterance`. Interim `asr.transcript` text is a
visual caption only; the single final becomes **one** voice `turn.submit`
(`input_mode: voice`, a new request id), read back as "Heard: …", and never
overwrites a typed draft. STOP, a new press and Netra losing focus discard the
capture (an accepted capture gets an empty closing frame; its late transcript
is ignored). A lost connection ends the capture and voice must be accepted
again. Ready 5 s, final 10 s and a 60 s press are client-local bounds, each
ending in an accessible status. Press-to-interrupt still silences playback
first, and no longer throws out of the key handler when the cancel cannot be
sent. Captions and voice status are shown but **not announced**: NVDA speaking
while the microphone is open would be recorded into the question.

**Voice is only claimed when it really works.** Today's server answers an
unknown `asr.start` with `INVALID_REQUEST`, which the client reports as
"Voice input is not available on this Netra server yet. Type your question
instead." It never sends a binary frame to a server that has not accepted the
capture (M1's endpoint closes the socket with 1003 on any client binary frame).
In fixture mode a press says voice needs a connection and never opens the
microphone.

### C1 review from the client side (for Arshad, before C1 merges)

The client implements the decided D-MIC fields plus the items marked
**proposed**; each is one place in the client if C1 decides otherwise.

1. `asr.start` (client → server envelope): `{capture_id: uuid, media_type:
   "audio/L16;rate=16000"}`; one request id per capture.
2. **Proposed:** the server answers `asr.ready {capture_id}` (same request id)
   before any binary frame is allowed, or a typed `error` with that request id
   to refuse (not configured, quota, provider down). Without an explicit
   acceptance the client cannot know it is safe to stream.
3. Binary frame: `[u32 big-endian header length][UTF-8 JSON header][audio]`,
   header exactly `{version: 1, capture_id, sequence, end_of_utterance,
   media_type}`, 16 KiB header cap (same shape as the approved server frames).
   `sequence` starts at 0 and is gap-free from the client.
4. Audio is L16 **big-endian** (RFC 2586/3551 define `audio/L16` in network
   order). Deepgram's `linear16` is little-endian, so the server swaps bytes, or
   C1 names little-endian explicitly and the client drops one swap loop.
5. `asr.transcript {capture_id, transcript_id: uuid, text, is_final}` with
   the asr.start request id. **Proposed:** exactly one `is_final: true` per
   capture, sent after the server has processed `end_of_utterance`, carrying the
   whole utterance. Deepgram emits several `is_final` segments per utterance, so
   the server aggregates (for example with Finalize). The client treats a final
   before its end frame as a caption and ignores any after the first.
6. **Proposed:** the client, not the server, turns the final into
   `turn.submit`. A server that also submitted would create two turns.
7. STOP/cancel needs no new message: an accepted capture gets an empty
   `end_of_utterance` frame; whatever the server then sends for it is ignored.
8. A disconnect ends the capture; microphone audio is never resent after a
   reconnect.
9. Frames carry at most 3200 audio bytes (100 ms) plus the header, so any C3
   total-frame limit of at least 4 KiB suffices on the client side.

## M1/M2/M3 boundary review (item 3)

M1's code was reviewed from its local branch `162e50b` (not published; M1's
push was blocked by its session policy):

- **Authentication.** `transport/http/auth.py` verifies the credential before
  accepting the socket, from `Authorization: Bearer` only; a failure closes
  with 1008. **M5 accepts this presentation for the client**, and the client
  now implements it. `/v1/ws`, `POST /v1/sessions` and the source-selection
  route are M1 proposals that are **not exposed**, and credential issuance
  and storage are undecided. The approval is therefore M5's side of INT-10
  only; it is not a merged contract.
- **Segments and audio.** `dispatcher.py` commits and sends `response.segment`
  text before `speak_segment` frames, with one sentence per segment. The
  captured transcript confirms this ordering, and the client relies on it
  for admission and ack identity. M1 **resends text only on replay, never
  audio**, which matches the client's fencing. Media type is part of the
  synthesizer config. M1's fixture uses `audio/mpeg`, which the client
  supports, but the real provider value is unset (INT-11b).
- **STOP and cancel.** M1 fences on every cancel reason identically. Using
  `user_stop` for press-to-interrupt is acceptable to both M1 and M5, so
  **Gap 6 is closed**.
- **Microphone.** M1's endpoint **closes with 1003 on any client binary
  frame**, and `speech/recognition.py` has no transport path. Real ASR
  capture therefore has no server to talk to (INT-11a).
- **Resume.** `_resume` returns a snapshot and the same pending
  `quiz.question`. That is what `ReconnectCoordinator` relies on.
- **Frame size.** There is still no wire limit. The client applies local
  bounds only (INT-11c).
- **M2.** Nothing is published (INT-01), and `jobs/v1/job.schema.json` is
  empty. Upload and job status stay fixture-only. No server-internal model
  was adopted as a public schema.
- **M3.** The video and evidence models in main are server-internal. No
  client-visible evidence, discovery or video-time/readiness payload exists.
  The fixtures stay, labelled.

## Playback and WebView dependency choice (prepared for review, not installed)

1. **Audio, now (no dependency).** The complete segment is played with WPF
   `MediaPlayer` from a transient file.
   - Measured on this machine: **first frame to player opened was p50
     270.8 ms and p95 293.4 ms** (n=20) for a 3 s WAV of about 96 KB. That
     time includes assembly, the temp write and the Media Foundation open.
   - Start latency grows with segment length. With M1's one sentence per
     segment it is bounded by the synthesis time of one sentence.
   - Staging writes the file on the UI thread. That is below a millisecond
     for sentence-sized audio, but review it if segments grow.
2. **Audio, if (1) is too slow against real TTS.** Two routes:
   - NAudio (MIT) with WASAPI output and incremental buffers, which enables
     play-while-receiving; or
   - direct WASAPI/COM interop with no package.
   The recommendation is to decide only after measuring (1) against real
   ElevenLabs sentence segments with M1. A package needs M5 review, the
   NuGet lock (M5-LOCK) and a version pinned at review time, not guessed
   here.
3. **Video.** `Microsoft.Web.WebView2` (WPF control) with the Evergreen
   WebView2 Runtime (preinstalled on Windows 11). Requirements:
   - Navigation is restricted to the YouTube embed origin; no devtools, no
     new windows and no other tabs.
   - Player control goes through the IFrame API
     (`pause`/`seekTo`/`getCurrentTime`, ready and unavailable events).
   - UI Automation for the host, with keyboard-only controls in WPF.
   Reviewers are M3 (time and evidence), M1 (session fields) and M5. The
   version is pinned at review time together with M5-LOCK.
